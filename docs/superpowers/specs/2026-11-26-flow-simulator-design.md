# 흐름 시뮬레이터 설계 (1차)

작성일 2026-11-26. 사용자가 2026-11-26에 질문 1~12와 설계 1~5절을 승인했습니다.

## 0. 배경과 결정

### 방향

제품의 중심을 바꿉니다. 사용자가 연동할 서비스 하나와 테스트 API 키를 넣으면 specmock이 세 가지를 합니다.

1. 그 서비스의 API 호출 흐름(시나리오)을 만듭니다.
2. 흐름을 도표로 보여 줍니다.
3. 화면에서 흐름을 mock과 실제 테스트 서버로 실행합니다.

specmock은 로컬에서 도는 개인 업무 도우미입니다. 호스팅, 공유, 로그인은 없습니다. 새 방향의 첫 시험 대상은 GitHub입니다.

### 지금 코드의 사실 (analyst 조사, 2026-11-26)

상세는 `.harness/flow-sim-facts-detail.md`에 있습니다. 경로는 `packages/core/src/` 기준입니다.

- 서비스 이름으로 스펙을 찾는 등록부가 없습니다. `ingest`는 origins가 비면 오류를 냅니다(`ingest/index.ts:136`).
- OpenAPI 경로를 큰 실제 스펙으로 돌린 적이 없습니다. `.specmock/stripe`는 markdown 문서 23개로 만든 기능 18개입니다. 공유 `$ref`는 `source.json`, `catalog.json`, `mockspec.json`에서 각각 펼쳐집니다. GitHub 스펙의 크기 영향은 추정이며 측정해야 합니다.
- 계약의 요청 본문은 선택 필드를 모두 채웁니다(`select/fixtures.ts:21`). 실제 GitHub POST가 422를 받을 가능성이 있습니다(추정).
- `Feature`는 응답 헤더, `requestBody.required`, 요청 예시, OpenAPI `links`를 버립니다(`analyze/openapi.ts:105-124`).
- 인증 헤더와 실제 서버 주소는 `target.json`의 자유 항목이라 GitHub에 그대로 맞습니다(`record/target.ts:26-33`).
- record 실행기는 값을 전달하지 않고, 정리하지 않으며, 첫 네트워크 오류에서 실행 전체를 버립니다(`record/index.ts:103-161`).
- mock은 한 구간짜리 경로 변수만 처리합니다(`generate/tsHono.ts:34-35`).
- 가림 규칙은 GitHub 토큰 접두어(`ghp_`, `github_pat_`)를 잡지 못합니다(`ingest/mask.ts:6-11`).

## 1. 구성

1차의 목표는 하나입니다. 사용자가 GitHub 스펙 URL과 테스트 토큰을 넣고, "issue 다루기" 흐름을 화면에서 mock과 실제 서버로 실행합니다.

### 새로 만드는 것 (core)

| 부품 | 하는 일 | 기대는 것 |
|---|---|---|
| `flow/infer` | 고른 기능에서 흐름을 추론합니다. 입력은 catalog의 기능 목록, 출력은 흐름 자료입니다. | catalog |
| `flow/run` | 흐름 하나를 대상 하나(mock 또는 실제)에서 실행합니다. 값 전달, 정리, 안전장치를 맡습니다. | `runContract`, masking, `target.json` |
| `flow/store` | 흐름 자료와 실행 결과를 서비스별 폴더에 읽고 씁니다. | workspace |

저장 위치는 `.specmock/<서비스>/flows.json`과 `.specmock/<서비스>/flow-runs/`입니다. `recorded/`는 기능 id가 열쇠라서 같은 기능이 두 번 나오는 흐름을 담지 못하므로 쓰지 않습니다.

### 고치는 것 (core)

- 요청 본문을 필수 필드만으로 만드는 선택지를 더합니다.
- `Feature`가 `requestBody.required`와 응답 헤더를 보존합니다. catalog의 해시가 바뀝니다.
- 큰 스펙을 처리합니다. 범위는 측정 결과로 정합니다. 1차의 기본 방침은 "기능을 고른 뒤 그 기능만 처리"입니다.
- 가림 대상에 `ghp_`, `github_pat_`를 더합니다.

### 화면과 MCP

- ui-server에 흐름 조회, 보완, 실행 경로와 안전장치 상태를 더합니다.
- web은 6단계 화면을 걷어내고 화면 2개를 둡니다: 서비스 등록 화면, 흐름 화면.
- MCP 도구 2개를 더합니다: 흐름 읽기, 흐름의 빈 연결과 본문 값 채우기.

### 1차에서 하지 않는 것

- 자원 그래프 화면 (2차)
- 내장 목록과 브라우저 탐색 (3차). 1차는 스펙 URL을 직접 받습니다.
- `Link` 헤더로 다음 페이지를 따라가는 일
- 여러 구간 경로 변수의 mock 처리
- 코드 생성기(TS·Java) 변경
- OpenAPI가 아닌 입력(문서 페이지)에서 흐름을 추론하는 일

### 가장 먼저 하는 일

GitHub 스펙을 측정합니다. ingest 시간, `source.json`과 `catalog.json`의 크기, 기능 수를 잽니다. 이 결과가 "큰 스펙 처리"의 범위와 처리 한도 값을 정합니다.

## 2. 흐름 자료와 추론 규칙

### 흐름 자료 (`flows.json`)

```
흐름
  id, 이름            예: issues, "issue 다루기"
  자원                예: issue
  단계[]
    단계 id           예: create_issue
    기능 id           catalog의 기능을 가리킴 (예: issues_create)
    역할              준비 | 본 단계 | 정리
    입력[]            경로 변수와 본문 필드마다 하나
      자리            예: path.issue_number, body.title
      출처            앞 단계 응답 | 사용자 값 | 고정 값 | 비어 있음
      근거            규칙 | Claude Code | 사용자
    만드는 자원       있으면 표시
```

- 입력마다 근거를 남깁니다. 화면은 근거별로 연결을 구분해 보여 줍니다.
- 추론을 다시 돌려도 근거가 "Claude Code"이거나 "사용자"인 입력은 지우지 않습니다.
- "만드는 자원"은 정리와 삭제 범위 제한이 씁니다.
- 서비스 공통 값(GitHub의 `owner`, `repo`)은 `target.json`의 `params`에 한 번만 둡니다. 모든 흐름이 이 값을 씁니다.

### 추론 규칙

1. **자원 찾기**: 경로를 자원 단위로 나눕니다. `/repos/{owner}/{repo}/issues/{issue_number}`에서 `issues`가 자원입니다. 목록 경로(`…/issues`)와 개별 경로(`…/issues/{issue_number}`)가 짝을 이룹니다.
2. **자원 순서**: 경로가 다른 자원의 개별 경로를 포함하면 그 자원이 먼저입니다.
3. **흐름 뼈대**: 자원마다 흐름 하나를 만듭니다. 순서는 부모 자원 준비 → 생성(목록 경로의 POST) → 조회(개별 경로의 GET) → 수정(개별 경로의 PATCH·PUT) → 정리(개별 경로의 DELETE)입니다. 선택한 기능에 있는 것만 넣습니다.
4. **값 연결**: 경로 변수 이름에서 자원 이름 접두어를 뗍니다(`issue_number` → `number`). 그 이름을 그 자원을 만든 단계의 응답 필드와 비교합니다. 맞는 필드가 정확히 하나일 때만 연결합니다. `{id}`와 `{<자원>_id}`는 응답의 `id`와 연결합니다.
5. **연결 실패**: 후보가 없거나 둘 이상이면 비워 둡니다. 추측으로 채우지 않습니다.
6. **본문**: 필수 필드만 넣습니다. 값은 스펙에 예시가 있으면 예시를 쓰고, 없으면 비워 둡니다.

### GitHub에서 예상하는 결과

아래는 analyst의 추정에 기댄 예상입니다. 실제 스펙으로 추론을 돌려 확인하는 일이 완료 조건 2입니다.

- 규칙이 찾는 것: 단계 순서, `issue_number ← number`.
- 비는 것: `{owner}`, `{repo}`, 본문 `title`의 값. repo를 만든 응답의 `name`과 `owner.login`은 변수 이름과 맞지 않습니다.
- 빈 자리는 Claude Code가 MCP 도구로 채우거나 사용자가 화면에서 넣습니다.
- GitHub issue는 삭제 API가 없습니다. 흐름에 정리 단계를 넣지 않고 "남은 자원"으로 알립니다. 흐름이 repo를 만들었다면 repo 삭제가 issue까지 지웁니다.

## 3. 순서 실행기 (`flow/run`)

실행기는 흐름 하나를 대상 하나에서 처음부터 끝까지 실행하고 단계마다 결과를 남깁니다. "둘 다"를 고르면 mock에서 한 번, 실제 서버에서 한 번 따로 실행합니다. 두 실행은 값을 섞지 않습니다.

### 단계 하나의 처리 순서

1. 입력을 채웁니다. 출처가 "앞 단계 응답"이면 같은 실행의 앞 응답에서 값을 꺼냅니다.
2. 빈 입력이 남아 있으면 요청을 보내지 않고 그 단계에서 멈춥니다. 빈 자리를 결과에 적습니다.
3. 안전장치를 확인합니다.
4. 요청을 보냅니다. 전송, 가림, 스키마 검사는 `runContract`를 다시 씁니다. `runContract`에 단계별로 본문과 헤더를 바꾸는 기능을 더합니다.
5. 응답을 가린 뒤 저장합니다. 단계가 자원을 만들었으면 "이번 실행이 만든 자원" 목록에 올립니다.

### 안전장치

- 켜짐(기본): 실제 서버 실행에서 GET이 아닌 단계를 보내지 않고 "안전장치로 건너뜀"으로 표시합니다. 그 단계의 응답이 필요한 뒤 단계도 함께 건너뜁니다. mock 실행은 모든 단계를 보냅니다.
- 꺼짐: 실제 서버에도 모든 단계를 보냅니다.
- DELETE는 대상 자원이 "이번 실행이 만든 자원" 목록에 있을 때만 보냅니다. 목록에 없으면 안전장치가 꺼져 있어도 실행기가 거부합니다.
- 토글 상태는 ui-server 메모리에만 둡니다. ui-server를 다시 시작하거나 서비스를 바꾸면 켜짐으로 돌아갑니다.
- 실행 요청마다 서버가 판정합니다. 화면을 거치지 않은 호출(MCP)도 같은 규칙을 따릅니다.
- 확인 창은 두지 않습니다.

### 정리

- 흐름이 끝나거나 중간에 실패하면 실행기가 만든 자원을 만든 순서의 반대로 지웁니다.
- 정리를 끈 실행은 지우지 않고 만든 자원 목록만 남깁니다.
- 삭제 API가 없거나 삭제가 실패한 자원은 "남은 자원"으로 결과에 적습니다. 주소와 식별자를 함께 적습니다.

### 실패 처리

- 단계가 2xx를 받지 못하면 뒤 단계를 멈추고 정리로 넘어갑니다.
- 네트워크 오류도 같습니다. 실행기는 그때까지의 결과를 저장합니다.
- 응답이 스키마와 다르면 실행을 멈추지 않고 "차이"로 표시합니다.

### 결과 저장

- 위치는 `flow-runs/<흐름 id>/<대상>.json`입니다. 흐름과 대상마다 마지막 실행 하나를 둡니다.
- 단계마다 보낸 요청, 받은 응답(가린 뒤), 상태, 걸린 시간, 건너뛴 이유를 담습니다.
- 실행 시작 시각을 적습니다. 이슈 #27이 지적한 문제(끝난 시각과 상수로 옛 결과를 판정)를 이 형식은 처음부터 피합니다.
- 테스트 토큰은 저장하지 않습니다. record의 가림 규칙을 그대로 씁니다.

### 이름 충돌

정리를 끄거나 정리가 실패한 뒤 다시 실행하면 같은 이름의 자원이 이미 있습니다. 실행기는 흐름이 만드는 자원의 이름 값에 실행마다 다른 꼬리(시각)를 붙입니다.

## 4. 화면

### ① 서비스 등록 화면

- 입력란 3개: 서비스 이름, 스펙 URL, 테스트 토큰. 토큰은 ui-server 메모리에만 둡니다.
- 대상 설정: 실제 서버 주소(스펙의 `servers` 첫 값으로 미리 채움), 공통 헤더, 공통 값.
- 기능 고르기: 기능을 묶음(tag)별로 접어 보여 주고, 고른 기능만 처리합니다. 전체 목록을 한 번에 그리지 않습니다.
- 등록이 끝나면 추론을 돌리고 흐름 화면으로 넘어갑니다.

### ② 흐름 화면

- 왼쪽: 흐름 목록. 흐름마다 빈 연결 수와 마지막 실행 상태를 표시합니다.
- 위쪽 줄: 흐름 이름, 대상 전환(mock / 실제 / 둘 다), 정리 켬·끔, 전체 실행, 오른쪽 끝에 안전장치 토글. 안전장치가 꺼져 있으면 위쪽 줄 색이 바뀝니다.
- 가운데: 순서도. 단계가 세로로 이어지고 단계 사이에 전달 값이 보입니다. 실행 전에는 연결의 이름(`number`)을, 실행 뒤에는 값(`number = 1`)을 보여 줍니다.
- 단계를 누르면 그 자리에서 펼쳐집니다. 보낸 요청과, mock 응답·실제 응답을 나란히 둡니다. 처음에는 차이가 난 필드만 보여 주고 "전체 보기"로 본문 전체를 엽니다.
- 아래쪽: 실행 뒤 "남은 자원" 목록. 주소와 식별자를 보여 줍니다.

### 단계의 상태 8종

실행 전, 성공, 차이 있음, 실패, 안전장치로 건너뜀, 입력이 비어 멈춤, 정리됨, 남은 자원. 색과 글자를 함께 써서 표시합니다.

### 빈 연결 채우기

- 빈 입력이 있는 단계는 순서도에서 "입력 필요"로 표시합니다. 펼치면 입력란이 나옵니다.
- 사용자는 값을 직접 넣거나 앞 단계의 응답 필드를 고릅니다.
- 연결마다 근거(규칙 / Claude Code / 사용자)를 작은 표지로 보여 줍니다. 사용자는 Claude Code가 채운 값을 고칠 수 있습니다.
- 빈 연결이 있어도 실행 버튼을 누를 수 있습니다. 실행기가 그 단계에서 멈추고 이유를 보여 줍니다.

### 1차에서 화면이 하지 않는 것

자원 그래프, 흐름 단계의 추가·삭제·순서 바꾸기, 실행 기록 비교, 색 주제 설정.

색, 글꼴, 세부 모양은 구현 전에 시안 페이지를 한 번 더 만들어 사용자의 확인을 받습니다. 지금 시안은 배치만 정했습니다.

## 5. 오류 처리, 테스트, 완료 조건

### 오류 처리

문구는 무엇이 잘못됐고 어떻게 고치는지를 적습니다.

| 상황 | 동작 |
|---|---|
| 스펙 URL을 읽지 못함, OpenAPI가 아님 | 등록 화면에서 멈추고 원인을 알립니다. |
| 스펙이 처리 한도를 넘음 | 한도와 실제 크기를 알리고 기능을 줄여 고르게 합니다. 한도 값은 측정 뒤 정합니다. |
| 고른 기능에서 흐름을 추론하지 못함 | 빈 흐름 목록과 이유를 보여 줍니다(예: 생성 기능이 선택에 없음). |
| 토큰이 없거나 실제 서버 주소가 비어 있음 | 실제 실행만 막고 mock 실행은 허용합니다. |
| 실제 서버가 401·403을 돌려줌 | 토큰과 권한 범위를 확인하라고 알립니다. 404 안내에도 같은 문장을 넣습니다. |
| mock 서버가 떠 있지 않음 | 실행 전에 mock을 만들고 띄웁니다. 실패하면 mock 실행만 실패로 표시합니다. |
| 정리(DELETE) 실패 | 실행 결과를 유지하고 그 자원을 "남은 자원"에 올립니다. |
| 흐름이 가리키는 기능이 스펙 갱신으로 사라짐 | 그 흐름을 "기능 없음"으로 표시하고 실행을 막습니다. 자료는 지우지 않습니다. |

### 테스트

- `flow/infer`: 작은 가짜 스펙으로 규칙마다 단위 테스트를 둡니다. 대상은 자원 찾기, 자원 순서, 접두어를 뗀 이름 일치, 후보가 둘일 때 비움, 재추론 때 사용자 값 보존입니다. GitHub 스펙에서 `issues`·`repos` 부분을 잘라 낸 파일로 추론 결과를 고정하는 테스트 1개를 둡니다.
- `flow/run`: 가짜 HTTP 서버로 테스트합니다. 대상은 값 전달, 빈 입력에서 멈춤, 안전장치 켜짐에서 건너뜀, 만들지 않은 자원의 DELETE 거부, 중간 실패 뒤 반대 순서 정리, 정리 실패 때 남은 자원 기록, 저장 파일에 토큰 없음입니다.
- ui-server: 흐름 조회·보완·실행 경로와 안전장치 상태(다시 시작하면 켜짐)를 테스트합니다.
- web: 상태 8종의 표시와 빈 연결 입력을 구성 요소 테스트로 확인합니다.
- 실제 GitHub 호출은 자동 테스트에 넣지 않습니다. 사용자가 테스트 토큰으로 실행해 확인합니다.

### 1차 완료 조건

1. GitHub 스펙 URL로 서비스를 등록하고 `issues`·`repos`에서 고른 기능이 처리됩니다. 측정한 시간과 파일 크기를 notes에 기록합니다.
2. 추론이 "issue 다루기" 흐름을 만들고, 규칙이 찾은 연결과 빈 연결이 화면에 구분되어 보입니다.
3. 빈 연결을 화면에서 채울 수 있고, Claude Code MCP 도구로도 채울 수 있습니다.
4. mock에서 흐름 전체가 실행됩니다.
5. 안전장치를 끄면 실제 GitHub에서 흐름이 실행되고, 실행기가 만든 repo를 정리합니다. 지울 수 없는 자원은 "남은 자원"에 나옵니다.
6. mock 응답과 실제 응답의 차이가 단계에 표시됩니다.
7. Stripe 작업 폴더(`.specmock/stripe`)가 깨지지 않고, 코드 생성기(TS·Java)의 지금 테스트가 통과합니다.
